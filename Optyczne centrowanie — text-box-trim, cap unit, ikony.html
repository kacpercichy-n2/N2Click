Optyczne centrowanie tekstu i ikon

Czerwona linia w każdym demo to prawdziwy geometryczny środek kontenera. Zwróć uwagę, gdzie względem niej ląduje środek liter — i jak to naprawić.

01Problem: half-leading

Przeglądarka centruje content area fontu (ascent + descent z metryk pliku), a nie realne glify. Ascent zawiera zapas na diakrytyki i overshoot, więc nawet przy line-height:1 blok liter siedzi za nisko. Im większy font-size i im „luźniejsze” metryki, tym bardziej to widać.

02Rozwiązanie natywne — text-box

Przycina half-leading do wybranych metryk fontu. cap = górna krawędź wersalika, alphabetic = baseline. Efekt: równy padding = realnie równy padding. Dodajesz to jako progressive enhancement — przeglądarki bez wsparcia po prostu renderują jak dziś.

/* skrót */
.btn {
  text-box: trim-both cap alphabetic;
  padding: 12px 20px;
}

/* longhand — to samo */
.btn {
  text-box-trim: trim-both;
  text-box-edge: cap alphabetic;
}

/* tekst obok ikony w flexie — trim zdejmuje też fałszywy offset */
.btn span { text-box: trim-both cap alphabetic; }

Wsparcie: Chrome 133+, Edge 132+, Safari 18.2+, Firefox 154+ (wcześniej za flagą). Globalnie ok. 80% i rośnie.

02bDwa fonty obok siebie — trim to wciąż za mało

Pułapka, w którą wpadliśmy w praktyce: data w foncie danych obok etykiety w foncie interfejsu, oba z text-box: trim-both cap alphabetic, kontener z align-items: center — i dalej offset. Matematyka: po trimie wysokość boksu każdego tekstu to jego własny cap-height, a te różnią się między krojami (np. 0.705em vs 0.745em). Centrowanie boksów o różnych wysokościach rozdziela różnicę po połowie na górę i dół, więc linie bazowe rozjeżdżają się o dokładnie (capA − capB) / 2 — a oko czyta tekst po baseline, nie po środku boksu. To błąd niezależny od monitora; DPR decyduje tylko, czy zobaczysz pół piksela rozmycia, czy pełny piksel skoku.

Rozwiązanie: dopełnij każdy przycięty boks od góry do WSPÓLNEJ wysokości H — padding-top: calc(H − 1cap). Jednostka cap to cap-height własnego fontu elementu, więc każdy tekst dostaje inną poprawkę, ale każdy boks kończy z identyczną wysokością H, której dolna krawędź to baseline. Centrowanie boksów ≡ wyrównanie linii bazowych — dokładnie, dla dowolnej pary fontów i rozmiaru.

Dobór H nie jest dowolny: baseline'y wyrówna KAŻDE wspólne H, ale pasmo glifów pary (baseline → wersalik wyższego kroju, wysokość max(cap)) siedzi przy dole boksu — względem sąsiadów centrowanych normalnie (ikona, badge) cała para zjeżdża o (H − max(cap)) / 2 w dół. Dla H = 1em to już ~0.13em (≈1.7px przy 13px) — widoczne gołym okiem. Dlatego H = max(capA, capB): składnik przesunięcia zeruje się, baseline'y wspólne, a pasmo glifów zostaje w optycznym środku. To jedna stała PER PARA fontów (jak ratio w capsize niżej), zapisana w em — skaluje się z rozmiarem.

AlgaAlga
trim + center — baseline'y ± (capA−capB)/2
AlgaAlga
+ padding-top: calc(var(--pair-cap) − 1cap)
/* Teksty w RÓŻNYCH fontach obok siebie we flexie z align-items: center */
.label-a, .label-b {
  text-box: trim-both cap alphabetic;
}
/* Normalizacja do H = max(cap) pary — jedna stała per para fontów.
   `cap` liczy się z WŁASNEGO fontu elementu, więc poprawka jest per font
   (dla kroju o większym capie wychodzi 0). Strażnik konieczny: bez trimu
   padding tylko przesuwa nieprzycięte boksy. */
@supports (text-box: trim-both cap alphabetic) {
  .label-a, .label-b {
    --pair-cap: 0.75em; /* cap-height WYŻSZEGO kroju pary */
    padding-top: calc(var(--pair-cap) - 1cap);
  }
}

Rachunek kontrolny z wdrożenia: Inter 13px → boks po trimie 9.16px (cap ≈ 0.705em); Plus Jakarta Sans 13px → 9.69px (cap ≈ 0.745em). Center bez poprawki: baseline'y ±0.27px (połowa z 0.53px różnicy). Normalizacja do --pair-cap: 0.75em: oba boksy 9.75px, baseline'y wspólne co do setnych, pasmo glifów w środku boksu z błędem 0.03em·px. (Pierwsza wersja tej poprawki używała H = 1em — baseline'y grały, ale cała para siedziała ~1.7px pod środkiem względem ikony i badge'a. Stąd reguła H = max(cap).) Wsparcie cap: Chrome 111+, Safari 17+, Firefox 97+ — starsze przeglądarki odrzucają całą deklarację calc() i zostają przy czystym trimie.

03Fallback, który działa wszędzie

Dwie drogi. (a) Capsize / ręczne pseudo-elementy z ujemnymi marginesami liczonymi z metryk fontu. (b) Nadpisanie metryk w @font-face — ascent-override / descent-override / line-gap-override. Wariant (b) jest najczystszy: naprawiasz font raz, a cały layout robi się przewidywalny.

Ag
bez korekty
Ag
capsize-style ::before/::after
/* (a) capsize-style — ratio bierzesz z pliku fontu (unitsPerEm) */
.trimmed {
  --cap: .72; --asc: .90; --desc: .22;
  line-height: 1;
}
.trimmed::before { content:""; display:block; margin-bottom: calc((var(--cap) - var(--asc)) * 1em); }
.trimmed::after  { content:""; display:block; margin-top: calc(-1 * var(--desc) * 1em); }

/* (b) normalizacja metryk fontu — działa w każdej przeglądarce */
@font-face {
  font-family: "Inter Trimmed";
  src: url(inter.woff2) format("woff2");
  ascent-override: 72%;   /* = cap height */
  descent-override: 0%;    /* = baseline  */
  line-gap-override: 0%;
}

/* (c) wyrównanie ikony do cap-height zamiast do x-height */
.icon { vertical-align: middle; margin-block-start: calc(1ex - 1cap); }

04bIle dokładnie przesunąć trójkąt — i dlaczego nie „na oko”

Dla trójkąta środkiem optycznym jest centroid, czyli średnia wierzchołków. Przy trójkącie skierowanym w prawo z pionową lewą krawędzią centroid leży w/3 od lewej, a środek bboxa w w/2 — różnica to dokładnie w/6. To jest cała korekta, jeśli ikona jest centrowana wg bboxa.

Haczyk, na który sam się nadziałem: większość zestawów ikon ma tę korektę już wbudowaną w path. Materialowe M8 5v14l11-7z ma bbox 8–19, czyli środek w 13.5 przy viewBoxie 0–24 — jest już przesunięte o 1.5 jednostki (6.25%). Dorzucenie kolejnych 6.5% to podwójna korekta i te ~2px w prawo.

Material +1.39% — poprawnie
path wg bboxa, bez korekty
ten sam path +7.64% = w/6

   Weź bbox path-a i porównaj ze środkiem viewBoxa.        */

//   bbox x: 8 → 19,  środek bboxa = 13.5,  środek viewBoxa = 12
//   wbudowana korekta = 1.5 jednostki (6.25%)

/* KROK 2 — policz cel: centroid = średnia wierzchołków */
//   (8 + 8 + 19) / 3 = 11.667  →  do 12 brakuje 0.333 = 1.39%

/* KROK 3 — zastosuj RÓŻNICĘ, nie regułę w ciemno */
.icon-play { transform: translateX(1.39%); }

/* Dla path-a centrowanego wg bboxa (M6.5 5v14l11-7z) pełna korekta:
   w/6 = 11/6 = 1.833 jednostki = 7.64% viewBoxa                     */
.icon-play-raw { transform: translateX(7.64%); }

/* Lepiej: przesuń viewBox zamiast transformem — zero kosztu w runtime
   i korekta skaluje się razem z ikoną.                              */
<svg viewBox="-0.333 0 24 24"><path d="M8 5v14l11-7z"/></svg>

Uwaga: translateX(%) liczy się od szerokości elementu SVG, nie viewBoxa — zgadza się tylko wtedy, gdy viewBox jest kwadratowy i wypełnia element. Przy preserveAspectRatio innym niż domyślny przesuwaj viewBox.

04cWielkość ikony zmienia wnioski — trzy „środki” rozjeżdżają się z rozmiarem

Asymetryczny glif w okrągłym kontenerze ma trzy konkurujące definicje środka: środek obrysu (bbox inku), centroid (środek ciężkości kreski) i circumcenter (środek okręgu opisanego na końcówkach = równy prześwit do obręczy). Dla symetrycznych kształtów pokrywają się; dla ptaszka, strzałki czy trójkąta — nie. I kluczowe: rozjazd między nimi skaluje się liniowo z rozmiarem glifu, więc ta sama formuła daje inny werdykt przy innej proporcji ikona/kontener.

Case (2026-08-07, tick powiadomień w N2Hub): lucide Check (M20 6 9 17l-5-5) w kółku 24 px (content 22 px). Końcówki (20,6), (4,12), (9,17) są równoodległe (8,54 jedn.) od punktu (12,9) — circumcenter leży aż 3 jednostki nad środkiem viewBoxa. Przy glifie 16 px (~70% średnicy koła) obrys↔circumcenter różnią się o 1,75 px — każda formuła coś poświęca: obrys → końcówka ramienia pod obręczą, circumcenter → masa czyta się nisko-lewo, centroid → pomiędzy, nadal źle. Żaden offset nie był „poprawny", bo problemem była proporcja, nie formuła. Po zmniejszeniu do 14 px (~58%) rozjazd spadł poniżej progu percepcji i zwykłe centrowanie po obrysie (viewBox="0 -0.5 24 24") zmierzyło 0,00/0,00 px od wizualnego środka obręczy.

/* REGUŁA: zanim dobierzesz formułę centrowania, sprawdź STOSUNEK
   glif/kontener. Orientacyjnie (glif = bbox inku, kontener = koło):
     ≤ ~55%  → centruj po obrysie; rozjazd formuł < progu rastra

               nie szukaj idealnego offsetu
   (lucide we własnym circle-check trzyma glif na ~45% średnicy).   */

05Kolejność działań

1. Ustaw text-box: trim-both cap alphabetic globalnie na buttonach, badge'ach, chipach.
1b. Teksty w różnych fontach obok siebie dodatkowo znormalizuj do wspólnej wysokości boksu H = max(cap) pary: padding-top: calc(var(--pair-cap) − 1cap) pod @supports — inaczej centrowanie rozjedzie baseline'y o (capA−capB)/2, a H większe od max(cap) opuszcza całą parę o (H − max(cap))/2 względem ikon i badge'y (sekcja 02b).
2. Dla własnego fontu dorzuć ascent-override/descent-override — zamyka temat w starszych przeglądarkach i przy SSR.
3. Ikony: display:block + flex/grid center, jeden spójny zestaw ikon. Na buttonach wyzeruj UA-owy padding (padding: 0) — bez tego grid przy ciasnym content boxie równa od lewej zamiast centrować.
3b. W kołach sprawdź proporcję glif/kontener (sekcja 04c) — powyżej ~65% średnicy najpierw zmniejsz ikonę; korekta offsetu nie uratuje za dużego glifu.
4. Dopiero na końcu ręczne korekty optyczne dla asymetrycznych kształtów.
5. Nie mieszaj: jeśli poprawiasz paddingiem, tracisz kontrolę przy zmianie fontu lub rozmiaru.
